# ADR-0003 — Compile `doctree-core` to WebAssembly for the in-browser walker

- **Status:** Accepted
- **Date:** 2026-06-02
- **Deciders:** Travis (user), agent
- **Supersedes:** —
- **Depends on:** [ADR-0001](ADR-0001-stack-tauri-rust-web3d.md), [ADR-0002](ADR-0002-graph-schema-and-gbnf-grammar.md)

## Context

A8 wired the desktop path: a Tauri command runs the deterministic walker
(`doctree-core`) over a document and streams the ordered build steps to the
frontend. But the product must also run as a **plain web app** — the user wants
to **host it publicly** so anyone can drop in a document and watch its graph
build, with **no desktop install**. In a normal browser there is no Tauri IPC,
so the A8 frontend fell back to a baked fixture; an uploaded document had nothing
to walk.

The walker is the **single source of truth** for the graph spine, and it is
already **pure Rust with zero native/LLM/GPU dependencies** — that decoupling is
the load-bearing invariant from ADR-0001. We need the *same* walker to run in the
browser without reimplementing it.

## Decision

**Compile `doctree-core` to WebAssembly** via a thin `wasm-bindgen` wrapper crate
and call it from the frontend. One authoritative walker, two compile targets:

- **Desktop (Tauri):** the existing native `build_steps`/`walk_document`
  commands (A8), compiled to the host target.
- **Browser (public hosting):** a new crate `crates/doctree-wasm` exposes the
  same `walk_document` / `build_steps` to JS, compiled to
  `wasm32-unknown-unknown` with `wasm-pack --target web`.

### `crates/doctree-wasm`

- A `cdylib`+`rlib` crate depending only on `doctree-core`, `wasm-bindgen`,
  `serde_json`, and (dev-ergonomics) `console_error_panic_hook`. All pure Rust —
  the ADR-0001 native-free invariant still holds; this adds **no** LLM/GPU/native
  code to the default build.
- Exports `buildSteps(text, minTermFreq?, minClauseWords?, maxTerms?)` and
  `walkDocument(text, …)` returning a **JSON string** (`serde_json::to_string`).
  Returning a string — rather than a `serde-wasm-bindgen` JS object — guarantees
  the wasm output is byte-for-byte the **same tagged shape** the Tauri command
  serializes (`[{"kind":"node","node":{…}}, …]`), so the frontend's
  `JSON.parse` path is identical for both engines. (It also avoids a dependency
  and the Map-vs-object ambiguities of structured cloning.)
- The serialization logic is factored into a private host-testable
  `build_steps_json` / `walk_document_json` so `cargo test -p doctree-wasm` runs
  on the host (the `#[wasm_bindgen]` exports themselves are exercised in the
  browser).

### Frontend wiring

`src/doc-source.ts` resolves the build sequence by engine:

- `isTauri()` → `invoke("build_steps", { text })` (native).
- otherwise → lazy-load the wasm module, `init()`, `JSON.parse(buildSteps(text))`.
- the baked fixture remains only as a last-resort fallback if the wasm module
  fails to load, so the page always renders something.

The wasm package is generated by `npm run build:wasm` (wasm-pack) and is a build
artifact (git-ignored); `predev`/`prebuild` npm hooks regenerate it so `npm run
dev` and `npm run build` are self-contained given the Rust + wasm-pack toolchain.

## Pinned invariant (the contract that must not silently drift)

- **Wasm output shape ≡ core build order:** `build_steps_json` round-trips to the
  same ordered, tagged steps as `doctree_core::build_sequence`. Pinned by
  `crates/doctree-wasm/src/lib.rs::tests::build_steps_json_matches_core_sequence`
  and `…::build_steps_json_is_frontend_tagged_shape`.
- **Native-free default build:** `doctree-wasm` pulls only pure-Rust crates;
  `cargo test --workspace` stays green with zero native deps (ADR-0001).

## Alternatives considered

1. **Reimplement the walker in TypeScript for the browser.** Pro: no wasm
   toolchain. Con: a second, drifting implementation of the most complex,
   authoritative piece of logic in the project — directly violates "the code is
   truth" (only the small, tested *build-ordering* mirror in `build-player.ts` is
   tolerated). Rejected.
2. **Walk server-side (a hosted API the browser calls).** Pro: no wasm. Con:
   introduces a cloud/server dependency into the core pipeline, against ADR-0001's
   "no cloud calls in the core pipeline," and complicates public hosting (now
   needs a backend, not a static site). Rejected.
3. **`serde-wasm-bindgen` returning JS objects** instead of a JSON string. Pro:
   marginally faster (no parse). Con: risks shape divergence from the Tauri JSON
   path (Map vs object, number/BigInt edges) and adds a dependency for no real
   gain at this scale. Rejected — fidelity beats micro-optimization here.

## Consequences

- The public web build and the desktop build run the **identical** Rust walker;
  fixing a walk bug fixes both. The graph spine cannot diverge between web and
  desktop.
- The frontend now `JSON.parse`s the same string shape from either engine; the
  Tauri command (A8) is retained as the native path and the future home of the
  B-stream LLM/embeddings work, which wasm can't host.
- Building the frontend now requires the Rust + `wasm-pack` toolchain (a CI/deploy
  prerequisite for public hosting). The generated package is git-ignored to keep
  binary artifacts out of the tree.
- A later genre/ontology change (ADR-0002 territory) automatically flows to the
  web build for free, since both targets share `doctree-core`.

## Anchors

- `crates/doctree-wasm/src/lib.rs` — `buildSteps`/`walkDocument` exports +
  `build_steps_json`/`walk_document_json` host logic + tests.
- `crates/doctree-wasm/Cargo.toml` — wasm-bindgen wrapper over `doctree-core`.
- `src/doc-source.ts` — engine resolution (Tauri native vs wasm vs fixture).
- `package.json` — `build:wasm` / `predev` / `prebuild` scripts.
